# CodeSpec UI 归档工作台与只读观测界面设计

## 1. 设计目标

将 CodeSpec UI 定位为“只读观测台 + Change 归档操作台”：

- 业务模块、Change、Spec 和工作流文档在 UI 中只读展示。
- 新增或修改业务数据必须通过 AI 工作流完成。
- 只有满足校验和 ARCHIVE 门禁的 Change 可以从 UI 发起归档。
- 归档操作必须复用现有 CodeSpec 归档事务，不能由前端重新实现归档规则。
- 页面需要让用户清楚区分当前生效内容、活动变更和历史归档内容。

本设计只描述 UI 信息架构、交互边界和视觉原则，不包含实现计划。

## 2. 最终信息架构

全局导航只包含以下入口：

1. 能力地图
2. 活动 Change
3. 可归档 Change
4. 归档历史
5. 系统主题入口（位于顶部，不作为独立页面）

文档不再作为独立导航模块。文档属于对应 Change，在 Change 详情中通过 Tab 查看：

- `proposal.md`
- `design.md`
- `spec.md`
- `tasks.md`
- `verification.md`

搜索保留在顶部全局搜索框，各业务页面保留与当前内容相关的筛选项，不设置独立“搜索与筛选”页面。

## 3. 全局导航与主题框架

### 3.1 导航结构

- 左侧固定导航显示五个业务入口。
- 顶部显示 CodeSpec 名称、全局搜索、当前工程名称和主题图标。
- 底部显示当前工程状态和“只读模式”提示。
- 不显示用户头像、用户名、登录状态、权限入口或账号菜单。

### 3.2 主题策略

主题入口提供三个选项：

- 深色
- 浅色
- 跟随系统（默认）

主题选择保存到本地 UI 偏好。跟随系统时根据操作系统的明暗模式实时切换。三种主题保持相同的信息结构、控件位置和交互语义，只调整背景、文字、边框、阴影和状态色。

### 3.3 只读边界

全局提示明确说明：

> 业务模块、Change、Spec 和文档均为只读；仅归档操作会写入工程。

## 4. 能力地图 / 业务模块

能力地图替代普通业务模块表格，用于展示系统能力及其关系。

每个模块卡片展示事实数据：

- 模块 ID 和名称
- 职责范围
- 当前 Spec
- 活动 Change 数量
- 最近归档时间
- 稳定、变更中或风险状态
- 依赖和被依赖关系

模块卡片只提供：

- 查看 Spec
- 查看关联 Change

不显示健康评分、百分比、环形评分或其他主观质量指标。模块新增和修改通过 AI 工作流完成，页面显示说明“仅可由 AI 工作流修改”。

## 5. 活动 Change

活动 Change 页面用于观察当前工作中的变更，不执行变更创建或推进。

列表支持按以下事实字段筛选：

- 状态
- 模式（feature、bugfix、refactor）
- 业务模块
- 最近更新时间

列表展示：

- Change ID 和标题
- 当前状态
- 变更模式
- 影响业务模块
- 任务进度
- Verification 状态
- 最近更新时间
- 下一阶段

点击 Change 后打开详情区域。页面只提供查看文档和关联 Spec 的入口，不提供创建、编辑、保存或状态推进按钮。

## 6. Change 详情与文档 Tab

Change 详情页包含：

- Change ID、标题、模式和状态
- 影响业务模块
- 任务进度
- Verification 状态
- ANALYZE → DESIGN → PLAN → IMPLEMENT → VERIFY → ARCHIVE 生命周期
- 关联 Change 和关联 Spec

文档内容嵌入详情页，通过 Tab 切换，不进入独立文档模块。文档区域支持 Markdown、YAML、代码块、表格和目录展示，始终显示“只读文档”。

只读操作包括：

- 查看关联 Spec
- 复制路径
- 在文件管理器中定位

不提供编辑、保存、删除、创建和状态修改操作。

## 7. 可归档 Change

这是 UI 中唯一具有写入能力的模块。

### 7.1 展示范围

页面展示归档候选 Change，并将其分为“可归档”和“暂不可归档”两类。可归档 Change 必须满足以下条件：

- Change 状态为 `ARCHIVE`
- 校验通过
- ARCHIVE 门禁通过
- Verification 证据完整且仍与产物绑定
- 无归档冲突
- 归档目标不存在

未满足条件的 Change 可以显示，但归档按钮必须禁用，并列出缺失原因，例如：

- 尚未进入 `ARCHIVE`
- 缺少 `archive-regression` 证据
- 验证证据过期
- 存在归档冲突

### 7.2 归档流程

页面流程固定为：

1. 查看可归档 Change
2. 查看归档预览
3. 查看 Spec 影响、归档目标、Change Index 更新和 Verification Receipt
4. 勾选“我已确认归档影响”
5. 点击“确认归档 Change”
6. 二次确认
7. 调用现有归档事务
8. 成功后重新构建 UI 索引

页面不能绕过校验或门禁。提交时后端必须再次读取最新状态并执行事务前检查，防止页面打开后 Change 状态发生变化。

### 7.3 失败处理

归档失败时：

- 显示明确错误原因。
- 显示事务已回滚或未产生部分写入。
- 保留当前页面状态，允许用户重新扫描。
- 不自动重试具有写入影响的操作。

## 8. 归档历史

归档历史只读展示已完成归档的 Change 与 Spec 追溯关系。

页面采用时间线形式，支持按 Change、业务模块、归档日期和归档状态筛选。

历史详情展示：

- Change 信息
- 归档时间
- 归档路径
- Verification Receipt
- 归档前后的 Spec 摘要
- 关联 Change
- 当前 Spec 链接

只提供查看 Change 文档、查看当前 Spec 和复制归档路径。不提供恢复、删除、编辑或重新归档。

后续修复或调整必须通过 AI 工作流创建新的 Change。

## 9. 数据与交互边界

UI 使用统一索引作为只读数据源，包含：

- 能力地图中的业务模块和依赖关系
- 活动 Change 摘要
- 当前生效 Spec
- 可归档 Change 的门禁与验证摘要
- 归档历史及其关联关系
- Change 详情中的文档产物

索引重建只刷新 UI 读取数据，不修改 CodeSpec 工程内容。归档是唯一允许写入工程的 UI 操作，并且必须调用现有事务接口。

## 10. 视觉与可用性原则

- 深色、浅色、跟随系统保持相同布局和信息层级。
- 紫色只用于当前选中、主要导航和归档主操作。
- 绿色表示通过、稳定或已归档。
- 黄色表示待处理或变更中。
- 红色表示失败、风险或冲突。
- 只读区域使用锁图标、只读标签和明确的说明文字。
- 禁用操作必须同时展示禁用原因，不能只依靠灰色按钮表达。
- 不使用主观健康分数替代可追溯事实。

## 11. 设计验收标准

- 用户能在全局导航中区分能力地图、活动 Change、可归档 Change 和归档历史。
- 用户不会误以为可以在 UI 中创建或编辑业务数据。
- 用户能在 Change 详情内通过 Tab 查看所有 Change 产物。
- 用户只能对满足门禁的 Change 看到可执行归档流程。
- 归档前能看到明确的 Spec 影响、历史路径和验证证据。
- 归档失败时不会产生部分写入。
- 深色、浅色和跟随系统模式下，状态语义和操作边界保持一致。
- UI 不引入独立文档阅读器、独立搜索页面或独立设置页面。
