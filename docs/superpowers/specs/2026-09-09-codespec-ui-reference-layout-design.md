# CodeSpec UI 手绘参考布局改造设计

## 1. 目标与边界

将当前 CodeSpec UI 严格调整为手绘参考图所表达的布局：左侧为工程与业务模块树，右侧为当前节点的文档工作区；顶部只保留全局搜索和重新扫描，底部保留主题与命令助手入口。

本次改造只改变 UI 的信息架构、页面布局和查看交互，不改变 CodeSpec 的 Change 生命周期、归档门禁、归档事务或文件扫描安全边界。业务模块、Spec、Change 和文档仍然只读；只有已经存在的归档操作继续允许写入工程。

手绘图中的 `api.yaml`、`interface.yaml`、`spec.md` 是工作区 Tab 的示例，不作为固定文件集合。UI 必须根据当前索引中的真实文档生成 Tab；不存在的文件不得伪造显示。

## 2. 目标页面结构

页面采用固定三层结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 左侧工程树                  顶部搜索框              重新扫描 │
├────────────────┬─────────────────────────────────────────────┤
│ codespec       │ 当前节点文档 Tab                           │
│ 工程名称       │ api.yaml / interface.yaml / spec.md         │
│                │ [结构化 / 源文件]                          │
│ 业务管理       │                                             │
│   模块 1       │ 文档阅读区                                  │
│   模块 2       │                                             │
│ 变更管理       │                                             │
│                │                                             │
│       ☀  ⌘    │                                             │
└────────────────┴─────────────────────────────────────────────┘
```

### 2.1 左侧工程树

左侧固定宽度，纵向滚动，内容顺序固定为：

1. `CodeSpec` 品牌和当前工程名称；
2. `业务管理` 分组；
3. 业务模块节点列表；
4. `变更管理` 分组；
5. 底部主题按钮和命令助手按钮。

模块节点使用 `UiIndex.businessModules` 渲染。模块节点是语义节点，不是 `codespec/` 文件系统目录。点击模块后，右侧工作区展示该模块关联的当前 Spec、模块文档和关联 Change。

`变更管理` 是左侧树中的固定节点。点击后，右侧工作区进入 Change 视图，并在工作区内部通过 Tab 或分区显示：

- 活动 Change；
- 可归档 Change；
- 归档历史。

不再在顶部显示独立的“业务功能”和“变更管理”导航按钮。

### 2.2 顶部工具区

右侧工作区顶部只保留：

- 全局搜索框，placeholder 为“搜索 Change、Spec 和计划”；
- `重新扫描` 按钮。

搜索仍覆盖 CodeSpec 文档和 Superpowers 计划，并继续使用现有只读搜索 API。重新扫描只刷新索引，不修改工程文件。

主题切换和命令助手不放在顶部，而放在左侧树底部，视觉上使用两个并列图标按钮。图标必须有可访问名称和悬浮提示。

### 2.3 右侧文档工作区

右侧工作区包含：

- 当前节点标题和必要的面包屑；
- 当前节点拥有的文档 Tab；
- `结构化视图 / 源文件视图`切换；
- 文档阅读区。

Tab 按当前文档实际存在情况动态生成。默认优先显示与节点最相关的 Markdown 或结构化文档。文档路径始终可见，并保留复制路径和文件管理器定位能力。

结构化视图规则：

- `metadata.yaml`、`tasks.yaml`、`verification.yaml` 等已有结构化解析文档可以显示结构化视图；
- Markdown 文档显示渲染后的 Markdown；
- 未提供结构化解析的 YAML 只显示源文件视图；
- 不能因为手绘图展示了接口表，就对任意文档推断或生成 API 表格。

## 3. 页面状态与交互

前端状态从当前的 `currentView = capabilities | changes` 升级为树节点状态：

```ts
type UiScreen =
  | { type: 'module'; moduleId: string; activeDocumentId?: string }
  | { type: 'changes'; tab: 'active' | 'archiveable' | 'history'; changeId?: string }
  | { type: 'change'; changeId: string; activeDocumentId?: string }
  | { type: 'search'; query: string };
```

### 3.1 模块节点

点击模块后：

1. 左侧模块节点高亮；
2. 右侧显示模块名称和工程/业务路径；
3. Tab 显示该模块的当前 Spec、关联文档和关联 Change；
4. 点击 Change 后在同一工作区查看 Change 详情；
5. 返回模块时保留之前选中的文档 Tab。

模块工作区展示事实数据：模块 ID、名称、职责、当前 Spec、活动 Change 数量、最近归档信息、关联关系。不存在的数据显示明确的空状态，不使用估算值或主观评分。

### 3.2 变更管理节点

点击 `变更管理` 后，右侧显示 Change 工作区。活动、可归档和归档历史都属于该工作区，不再作为顶部导航页面。

Change 列表继续显示：Change ID、标题、状态、SDD 等级、模式、影响模块、任务进度、Verification 状态和下一阶段。点击 Change 后切换到 Change 详情。

Change 详情继续保留现有生命周期 stepper：

```text
ANALYZE → DESIGN → PLAN → IMPLEMENT → VERIFY → ARCHIVE → ARCHIVED
```

详情文档使用动态 Tab。详情页保留门禁面板、Verification 信息、关联模块、关联 Spec 和只读文档内容。

### 3.3 归档操作

归档仍然是 UI 唯一允许写入工程的操作。可归档 Change 必须继续经过现有后端归档事务和最新门禁检查。左侧树只提供进入归档候选工作区的入口，不直接执行归档。

归档预览和确认流程保持现有设计：展示 SDD 等级、Spec 影响、归档目标、Change Index 更新、Verification Receipt，用户确认影响后再执行二次确认和归档事务。

## 4. 现有实现映射

### 4.1 页面壳层

- `src/ui/web/index.html`：移除顶部业务导航按钮，增加左侧树容器和底部工具区。
- `src/ui/web/styles.css`：启用双栏布局；左侧固定宽度，右侧可滚动；保留现有主题变量和响应式能力。
- 顶部搜索和重新扫描保留现有 DOM 标识，避免改变已有 API 绑定。

### 4.2 前端渲染

- `src/ui/web/app.js`：新增树节点渲染和模块工作区渲染。
- 将现有 `renderCapabilities()` 的模块卡片网格改为模块节点选择后的详情工作区。
- 将现有 `renderChangesWorkspace()` 作为变更管理工作区的内容渲染器，移除其对顶部导航的依赖。
- 复用 `renderChangeDetail()`、生命周期 stepper、门禁面板和文档 Tab，不重新实现 Change 领域规则。
- 关闭或改造独立 `openDocument()` 页面，使文档优先在右侧工作区中打开；搜索结果仍可以进入统一文档工作区。

### 4.3 索引数据

现有 `UiIndex` 已包含业务模块、当前 Spec、活动 Change、归档候选和归档历史，可作为新布局的主要数据源。模块工作区所需的职责、依赖和最近归档信息若当前索引缺失，应从已有 canonical 数据补充；不得在前端硬编码。

Change 文档 Tab 必须继续使用 `UiChangeGroup.documents` 动态生成。新增的结构化视图不得改变现有 `structuredContent` 的解析范围。

## 5. 错误与空状态

- 没有业务模块：左树保留 `业务管理`，右侧显示“暂无业务模块”和 AI 工作流提示。
- 模块没有当前 Spec：显示明确的“当前 Spec 未建立”，不显示空白文档区。
- 模块没有关联 Change：显示“暂无关联 Change”。
- 文档解析失败：保留源文件视图，并显示解析失败说明。
- 搜索无结果：在右侧工作区显示搜索空状态。
- 重新扫描后当前模块、Change 或文档已消失：回退到对应分组并提示索引已更新。
- 归档失败：保留当前工作区状态，显示明确错误和事务未产生部分写入的结果，不自动重试。

## 6. 响应式规则

桌面端严格采用手绘图的左树右工作区布局。窄屏下：

- 左侧树收缩为可展开抽屉；
- 右侧工作区占满宽度；
- 文档 Tab 支持横向滚动；
- 主题与命令助手仍位于树抽屉底部；
- 不改变文档和 Change 的只读/归档边界。

## 7. 验收标准

1. 页面视觉结构为左侧工程树、右侧工作区，顶部不再出现“业务功能 / 变更管理”并列页面按钮。
2. 左侧显示当前工程名称、业务管理、业务模块和变更管理，底部显示主题与命令助手入口。
3. 点击模块后，右侧显示该模块的文档、当前 Spec 和关联 Change。
4. 点击变更管理后，右侧显示活动 Change、可归档 Change 和归档历史。
5. 点击 Change 后，右侧显示生命周期、门禁、关联信息和动态文档 Tab。
6. 文档 Tab 只显示索引中真实存在的文件，不固定伪造 `api.yaml` 或 `interface.yaml`。
7. 结构化/源文件切换只在文档确实支持结构化渲染时显示。
8. 搜索和重新扫描功能保持可用，且不改变文件。
9. 归档仍是唯一写入入口，并继续复用现有归档事务和后端门禁。
10. 主题、命令助手、空状态、错误状态和窄屏布局均不破坏上述信息层级。

## 8. 测试范围

- 更新 UI 渲染测试，覆盖左侧树节点、模块工作区、变更管理工作区和 Change 详情。
- 覆盖模块无 Spec、无关联 Change、文档缺失、搜索无结果和重新扫描后节点消失等状态。
- 覆盖动态文档 Tab 不显示不存在的示例文件。
- 覆盖结构化视图仅对支持的 YAML 文档出现。
- 保留现有归档预览、门禁失败、事务失败和索引重建测试。
- 完成桌面宽度和窄屏宽度的浏览器验收，确认树、Tab、文档滚动和底部工具区可用。
